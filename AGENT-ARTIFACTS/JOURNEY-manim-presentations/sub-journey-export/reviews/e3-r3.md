## HIGH

### H1. The privacy default (`--transcript none`) has no test: a default of `full` passes the whole suite
- Location: `manim_presentations/cli.py` export subparser, `default="none"`. Tests: `tests/export/frames_plugin.py:49-51` and `tests/export/test_transcript.py:23`.
- Principle: tests must be falsifiable. This is a ★ item ("transcript none/narration/full with exact privacy"), and PLAN §3.9 says "(default `none`)".
- Mutant `default-transcript-full` (`default="none"` → `default="full"`): **SURVIVED**. All 24 export tests passed.
- Why: every privacy check exports with an explicit `--transcript <mode>`. The only exports without the flag are in `test_file.py`, and they never look for script text.
- Impact: a talk exported the way most users export it (no flag) could ship every private `>` note, and CI would stay green.
- Fix (zero extra encodes): in `test_every_frame_of_every_beat_is_the_builds_frame_at_the_asked_size`, which already exports without the flag, assert the following on `everywhere(html)` (move `everywhere`, `NARRATION` and `NOTES` into `frames.py`):
  - no line of NARRATION + NOTES is present;
  - `manifest(html)["transcript"] == "none"`.
  Then re-run the mutant and see it go red.

### H2. The ★ no-black-frame test still cannot see the outgoing video blank or rewind
- Location: `tests/export/frames.py:141-144`, and the docstring at `:133-134`.
- Principle: exact checks, not exhaust. Each named test must kill its own mutant. This is the ★ item "no black frame on any transition". It repeats r2 H1.
- Defect: the r2 fix records `seeking`, but it accepts `c == 0 and seeking` for **every** outgoing beat. r2 asked for this exception only when `old == LOOP`. The docstring says it is "a loop's wrap", but the code does not restrict it to that. Code 0 means the canvas reader gave up (`readyState < 2`), so it is exactly "unreadable or black". Also, any frame of the outgoing beat is accepted, so the outgoing video may jump backwards during a transition.
- Mutants, injected after `stage.prepend(v)` in `show()`:
  - `outgoing-seeks-forever`: `if (front) { front.pause(); front.currentTime = 0.02; }`. Against `test_every_transition…` alone: **SURVIVED**. Against all player tests except `presses_faster`: **SURVIVED** (8 passed).
  - `outgoing-rewinds-at-insert`: `if (front) front.currentTime = 0;`. Against all player tests except `presses_faster`: **SURVIVED**.
  - Both are killed only by `test_presses_faster…`. That kill is incidental: its `<= {0, 2}` set check sees the code-0 entries. A test about stale shows should not be the only guard of the ★ property.
- Fix:
  1. Restrict the exception to the loop: `(c == 0 and seeking and old == LOOP)`.
  2. Record the outgoing element's code just before the press (`T.before = T.code(T.old)` in the same `evaluate` as `T.old`).
  3. For a non-loop outgoing beat, require every outgoing entry to be `>= before`. A held or ended video never moves back, and a playing one only moves forward.
  4. Fix the docstring to say exactly that.
  5. Re-run both mutants against `-k every_transition` alone. Both must go red.

### M1. "No neighbour is decoded before the shown clip has its source" is claimed as tested, but the r2 M3 mutant survives
- Location: `player.html:94` and `:103`. DECISIONS (E1+E2 r2 resolutions, "Blob window") says the rule is "both tested through the ledger". Test: `test_player.py:108-111`.
- Principle: no spec drift (DECISIONS must be true), lower latency, and every named rule needs a mutant that a test kills.
- Mutants:

  - `neighbours-decoded-before-src`: decode the neighbours right after `v.src =`, still before the swap. **SURVIVED**.

- Fix: in the `createObjectURL` hook, record `[blob, T.video() === T.old]`, where the second field is "the old element is still in front". Then assert:
  - the first Blob made in an action is the target beat;
  - every other Blob is made after the swap.
  Both mutants then go red. Otherwise correct DECISIONS.

### M2. Playback of every Next waits behind a neighbour's base64 decode
- Location: `player.html:94-95`. `windowAt(beat)` runs before `v.play()` in the `seeked` handler.
- Principle: lower latency. Only load-bearing work may sit on the critical path. r2 M3's intent was only half done: the decode moved off the swap, but it still blocks the start of playback.
- Defect: on Next from i to i+1, the handler synchronously decodes beat i+2's base64 (r2 measured 167 ms per 8 MiB, one 30 s beat at P4's rate). Only then does it call `play()`. So frame 0 sits paused for that long on every Next. A jump decodes up to two neighbours first.
- Fix: one reorder. Call `if (play) v.play()…` first, then `windowAt(beat)`. A test can pin this: log a `play` marker into the ledger, and assert it comes before the neighbour's `createObjectURL`. This can share the M1 ledger change.
