- Evidence: CI run 41184605858 (macos-latest), `1 failed, 233 passed in 1271.96s`. Failing test: `tests/export/test_player.py::test_the_jump_list_follows_the_position_so_a_jump_back_works[chrome]`, at test_player.py:62 (the second jump to `d`, from the loop `c`). frames.py:166 failed with log `[[768, False, False, True], [1024, True, False, True]]`. The expected frame was `frames[3] − 1 = 24`.
- Mechanism (inferred, not proven): the fresh element showed frame 0 at `loadeddata`. It then seeked paused to 24.5/25 s. In Chrome on the loaded 3-vCPU runner, `seeked` fired before the seeked frame reached what `drawImage` reads. So the player raised an element whose current picture was still frame 0. If the screen follows the same picture, the viewer sees d's first frame flash before its last frame. That breaks the north star's "no black and no wrong frame on any transition", and DECISIONS' claim that `seeked` on a fresh element is exact in Chrome. Local Chrome passes (33/33 here), and r4's CI passed, so this case is a load-dependent race, not a constant failure.
- Principles: the shiny item "no wrong frame on any transition"; the guard must be exact, not timing-dependent; CI must be green before the period ends.
- Fix: the parent decides the route; this review does not pick one. First, a probe on macos-latest: repeat paused shows of a last frame in Chrome, about 100 of them, under the suite's load. At each `seeked`, record the canvas code, then record it again at that element's next `requestVideoFrameCallback` (Chrome fires rVFC after a paused seek, P4) and in a screenshot. If only the canvas lags, the route is sound and the test must read the frame at the next presented frame (Chrome's rVFC). If the screen lags too, the Chrome swap needs a presented-frame signal: rVFC in Chrome, and `seeked` stays in WebKit, where rVFC never fires after a paused seek (P5). That would be two marked cases, the same shape P5 already sanctioned. Do not re-run CI until it is green and call it fixed: a pass does not prove this race is gone.
